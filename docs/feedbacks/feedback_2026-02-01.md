## EXECUTIVE SUMMARY

You have a solid foundation (protocol lock, workstream boundaries, skeleton, gates, contract v1). But you are **not ready for full-scale autonomous deployment** yet because several task interfaces that agents rely on are either **missing**, **under-specified**, or **implicitly assumed**.

### Critical blockers (must fix before launching the swarm)

1. **Registry is empty + registry schema is underspecified.**
   `registry/rollup_registry_v1.csv` has only a header, and tasks assume it already contains rollup rows, source key mappings, and parseable address JSON. That’s almost certain to cause immediate drift/blocking (joins, attribution, and even basic rollup_id semantics).
2. **Processed-manifest standardization comes too late.**
   Many tasks require `data/processed_manifest/*`, but the helper script to generate them is only in T096 with no dependencies pointing to it. This will produce inconsistent provenance (or missing manifests) across ETL/data-product tasks.
3. **Several tasks reference docs that appear not present in the repo.**
   E.g., T080/T094/T095 reference `docs/end_to_end_*`. If those are not in HEAD, agents will be forced to improvise, which is exactly what your governance forbids.
4. **On-chain extraction (T087) is too large and too “blob-uncertain” as a single task.**
   Without a *specific blob-readiness acceptance test*, it’s highly probable you spend days extracting data only to discover your RPC/provider doesn’t expose the fields you need (type‑3 tx payload/receipt blob fields).
5. **Issuance definition and EIP‑7918 counterfactual assumptions aren’t locked in W0.**
   Those are scientific/definition choices; if you leave them to W1/W6 workers, you’ll get either blocking or silent assumption drift.

### Top recommendations (do these first)

1. **Promote registry to a first-class contract and seed it immediately** (even if only “top N rollups + canonical rollup_id choice + source keys”). Then make T030 depend on it.
2. **Run T096 first and add it as a dependency to any task producing processed manifests.** If you want reproducibility, processed manifests cannot be “optional style.”
3. **Split T087 into smaller tasks with explicit acceptance tests for blob tx fields.** Don’t attempt full extraction before you prove your provider supports blob fee computation.
4. **Add missing core empirical analysis tasks** (trend tests, break tests, elasticity regressions, decomposition charts, blob-regime charts). Right now you have “plots,” not “hypothesis tests.”
5. **Lock issuance definition + EIP‑7918 parameterization in W0** (contracts/decisions + contracts/assumptions), then let ETL/analysis implement deterministically.

## CROSS-CUTTING CONCERNS

### Path Conflicts and File Organization

* **Main risk:** shared directories with prefixes in allowed_paths are mostly safe because tasks have unique filenames.
* **But:** “directory-prefix” allowed paths (e.g., `data/processed/panels/`) allow multiple tasks to write arbitrary new files. You mitigated with `parallel_ok: false` for panel tasks; keep that discipline.
* **Recommendation:** For any task marked `parallel_ok: true`, avoid allowing broad directory prefixes unless absolutely necessary (you did this correctly for T083–T086 by using source-specific directories).

### Contract and Protocol Compliance

* **Good:** Tasks consistently mark protocol/contracts as read-only.
* **Gaps:**

  * No contract for on-chain rollup cost tables (T088 outputs are not contract-defined).
  * Issuance and counterfactual are not locked, so compliance is currently impossible.
* **Recommendation:** Expand contracts before the swarm reaches those tasks.

### Success Criteria and Testability

* **Weak points:**

  * ETL tasks don’t define minimal schema checks (column names/types) as success criteria.
  * Validation scripts don’t specify exit codes and exact JSON schema.
  * Full-panel analysis tasks commit outputs that CI cannot regenerate (because processed data is gitignored).
* **Recommendation:** Standardize:

  * “schema assertions” in ETL outputs,
  * “exit code + JSON schema” for validation,
  * “sample-mode committed outputs” for analysis tasks.

### Completeness Gaps

Relative to your research plan objectives (trend, breaks, elasticity, regimes, decomposition, issuance share, counterfactual):

* Missing explicit tasks for:

  * STR trend tests (Mann–Kendall + NW regression),
  * structural break tests (Dencun boundary),
  * elasticity regressions (rent vs L2 scale),
  * decomposition plots over time (burn vs tips; blob vs execution),
  * blob fee “at-minimum fraction” charting and linkage to STR,
  * rollup burn vs issuance time series.
    You have the data plumbing tasks, but not the empirical analysis tasks.

## RISK ASSESSMENT

### 1) Blob-field availability and correctness (highest risk)

* **Risk:** High. It’s probable your first RPC provider won’t expose all blob tx fields consistently, especially `blobVersionedHashes` or receipt blob fields, leading to incorrect `burn_blob`.
* **Mitigation:**

  * Add an explicit “RPC blob capability probe” task and do not proceed to full extraction until it passes.
  * Prefer receipt-provided blob fee fields if available; else lock the EIP‑4844 computation in W0.

### 2) Registry drift / attribution incompleteness

* **Risk:** High. Batcher/poster addresses change; evidence is messy.
* **Mitigation:**

  * Enforce structured address objects with validity windows + confidence + evidence URLs.
  * Maintain an “unattributed spend” bucket and a candidate-address report as a first-class output.

### 3) Provenance erosion via inconsistent processed manifests

* **Risk:** High if T096 not sequenced first.
* **Mitigation:** Make processed manifests mandatory and standardized early.

### 4) Swarm-unfriendly endpoint discovery (L2BEAT/Blobscan)

* **Risk:** Moderate to high. Interactive discovery is brittle for autonomous agents.
* **Mitigation:** Require curlable discovery procedures and store endpoint schemas in sample READMEs.

### 5) Scientific-definition drift (issuance, counterfactual parameters)

* **Risk:** Almost certain without W0 locks.
* **Mitigation:** Lock definitions in W0, and block downstream tasks by dependency until done.

### 6) Full-scale outputs not reproducible in CI (processed data gitignored)

* **Risk:** Moderate. Judges cannot verify full-panel figures without external data.
* **Mitigation:** Ensure every analysis task has `--sample` mode with committed sample outputs and store full-run provenance via manifests.
